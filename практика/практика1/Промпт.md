Ты — senior/staff Python backend engineer в крупной tech-компании уровня Яндекса. Твоя задача — сгенерировать не учебный pet-project, а реалистичный production-like backend-сервис, максимально похожий на внутренний сервис большой технологической компании.

Мне нужен проект, на котором я смогу практиковаться как junior/middle backend developer, решая реальные инженерные задачи, похожие на рабочие тикеты.

Сгенерируй проект по следующим правилам.

## 1) Общая цель

Создай backend-сервис уровня “реальный сервис крупной компании”, а не “демо CRUD”.
Проект должен выглядеть так, будто:

* его пишет команда из нескольких backend-разработчиков;
* он уже какое-то время живет в production;
* в нем есть legacy-решения, техдолг, баги, недоделанные места;
* он должен выдерживать рост нагрузки;
* в нем важны надежность, читаемость, расширяемость, наблюдаемость и безопасность.

## 2) Технологический стек

Используй:

* Python 3.12+
* FastAPI
* PostgreSQL
* SQLAlchemy 2.0 async
* Alembic
* Redis
* Celery или Dramatiq для фоновых задач
* Docker + docker-compose
* pytest
* JWT / OAuth2
* Pydantic v2
* structured logging
* OpenAPI / Swagger
* pre-commit
* ruff / mypy
* optional: Kafka или mock event-bus abstraction, если уместно

## 3) Архитектура

Сделай архитектуру похожей на реальный коммерческий backend:

* API layer
* service layer
* repository/data-access layer
* domain models / entities
* background jobs
* integrations
* config management
* observability
* tests
* migrations

Примерно такая глубина:

* routers/
* services/
* repositories/
* models/
* schemas/
* tasks/
* core/
* db/
* integrations/
* utils/
* tests/

Добавь:

* dependency injection через FastAPI Depends или отдельный container-подход
* настройки через env
* разделение конфигов по окружениям
* централизованную обработку ошибок
* middleware
* healthcheck/readiness/liveness endpoints

## 4) Предметная область

Выбери реалистичную бизнес-доменную область, достойную большой компании.
Не делай слишком банальный todo-list.
Подойдут, например:

* сервис управления доставками и слотами доставки
* платформа бронирования и распределения ресурсов
* сервис заказов и возвратов
* внутренний сервис обработки заявок/воркфлоу
* сервис управления рекламными кампаниями
* billing/subscription service
* moderation/review pipeline
* B2B marketplace backend

Выбери одну доменную область и подробно опиши:

* что это за сервис,
* его роль в общей системе,
* кто его пользователи,
* какие у него ключевые сущности,
* какие бизнес-ограничения,
* какие edge cases важны.

## 5) Требования к “реалистичности”

Проект должен включать признаки реального production-кода:

* неидеально одинаковый стиль в разных модулях
* несколько legacy-участков
* технический долг
* неочевидные баги
* куски кода, которые хочется отрефакторить
* не везде оптимальные запросы
* не везде корректная обработка ошибок
* местами недостающие тесты
* местами спорные архитектурные решения

Но:

* проект должен оставаться рабочим;
* баги и техдолг должны быть реалистичными, а не абсурдными.

## 6) Что обязательно должно быть в проекте

Добавь:

* CRUD не только базовый, но с реальными бизнес-правилами
* pagination / filtering / sorting
* soft delete хотя бы для части сущностей
* optimistic/pessimistic locking где уместно
* idempotency хотя бы для одного критичного endpoint
* rate limiting или заготовку под него
* RBAC / roles / permissions
* audit log
* background jobs
* retry logic для внешних интеграций
* кеширование через Redis
* transaction management
* concurrency-sensitive кейс
* хотя бы одну внешнюю интеграцию через абстракцию клиента
* экспорт/импорт данных или batch processing
* feature flags или хотя бы простую реализацию toggles
* metrics/logging/tracing-friendly structure
* seed-данные для локального запуска

## 7) Наблюдаемость и эксплуатация

Добавь production-like operational aspects:

* structured JSON logging
* correlation/request id
* healthcheck endpoints
* базовые метрики
* конфигурируемые таймауты
* graceful error handling
* понятные сообщения в логах
* README с инструкцией запуска, миграций, тестов, линтеров
* docker-compose для локальной среды

## 8) Безопасность

Добавь realistic security considerations:

* JWT auth
* роли пользователей
* проверка прав доступа
* валидация входных данных
* безопасная работа с секретами через env
* защита от очевидных ошибок в обработке пользовательского ввода
* не хардкодь секреты

## 9) Тесты

Добавь тесты, но не 100% покрытие.
Пусть будет реалистично:

* часть тестов есть,
* часть отсутствует,
* местами тесты хрупкие,
* местами не покрыты edge cases.

Нужны:

* unit tests
* integration tests
* хотя бы несколько API tests

## 10) Документация внутри проекта

Сгенерируй:

* README
* краткое описание архитектуры
* список известных проблем / tech debt
* список TODO
* примеры env-переменных
* несколько примеров запросов к API
* краткое описание модели данных

## 11) Самое важное: задачи для практики

После генерации проекта создай backlog из 25–40 задач, как будто это реальные тикеты в Jira для стажера / junior / middle backend developer.

Раздели задачи по уровням:

* 10–15 задач уровня intern/junior
* 10–15 задач уровня junior+
* 5–10 задач уровня middle

Типы задач должны быть максимально реалистичными:

* bugfix
* добавить endpoint
* исправить некорректную бизнес-логику
* починить N+1 query
* добавить индексы в БД
* исправить гонку/конкурентный баг
* написать тесты
* покрыть негативные сценарии
* рефакторинг сервиса/репозитория
* декомпозиция слишком большого модуля
* корректная обработка транзакций
* добавить audit logging
* исправить кеш-инвалидацию
* улучшить схему API
* добавить фильтры/сортировки/пагинацию
* исправить проблему в фоновой задаче
* починить идемпотентность
* исправить права доступа
* улучшить observability
* устранить баг миграции
* адаптировать код под feature flag
* исправить flaky test
* стабилизировать интеграционный тест
* добавить retry/timeout/circuit-breaker-like поведение для интеграции

Для каждой задачи укажи:

1. ID тикета
2. Название
3. Тип
4. Уровень сложности
5. Контекст
6. Симптомы или проблема
7. Что ожидается в результате
8. Где искать в коде
9. Какие файлы вероятнее всего менять
10. На что обратить внимание при решении
11. Как примерно проверить, что задача решена

## 12) Формат выдачи

Ответ должен быть в таком порядке:

1. Название сервиса
2. Краткое описание бизнеса
3. Архитектурное описание
4. Структура проекта по папкам
5. Модель данных
6. Ключевые API endpoints
7. Где специально заложены баги, техдолг и спорные решения
8. Полный исходный код проекта
9. README
10. Backlog задач intern/junior/middle
11. Отдельно список “скрытых проблем”, которые не надо сразу раскрывать в тексте задач, чтобы я мог искать их сам

## 13) Ограничения

Важно:

* не упрощай проект до pet-project
* не делай его “идеально чистым”
* не делай все задачи искусственными
* избегай игрушечных сущностей
* архитектура должна быть правдоподобной для большой компании
* код должен быть таким, чтобы с ним можно было реально работать несколько недель
* используй реалистичные названия сущностей, сервисов, таблиц, ошибок, background jobs
* задачи должны быть похожи на настоящие рабочие тикеты, а не на задания из курса

## 14) Дополнительный режим реализма

Добавь ощущение, что проект уже живет:

* есть changelog последних изменений
* есть несколько “известных инцидентов” или постмортем-кратких заметок
* есть пара временных костылей “сделано временно, потом исправить”
* есть legacy endpoint, который нельзя просто удалить
* есть компромиссные решения из-за сроков

## 15) Что я хочу получить в итоге

Я хочу использовать этот проект как симуляцию работы backend-разработчика в крупной компании уровня Яндекса:

* брать тикет,
* разбираться в чужом коде,
* искать баг,
* писать фикс,
* добавлять тесты,
* не ломать существующую логику,
* работать с миграциями, БД, транзакциями, интеграциями, очередями и кэшом.

Поэтому делай результат максимально приближенным к реальности.

В конце отдельно предложи:

* с какого тикета лучше начать стажеру,
* какие 5 задач дадут лучший рост junior backend developer,
* какие 3 задачи уже ближе к уровню middle.
